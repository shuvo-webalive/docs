The Blogs API has twelve endpoints, and you can call every one from all seven SDKs. Every path starts with `/api/v4/admin/blogs`.

<Warning>
  **Replacing a blog post resets the fields you leave out of the body.** `PUT` sets `content` to
  `null`, `is_published` to `false`, `date` to the current time, `categories` to the store's default
  category, `seo_configs` to `{"meta_tag": []}`, `visible_to` to `null` and `selected_customers` to
  `[]`. It keeps the image and `created_by`, and keeps `url` unless you send a new one. To change
  only some fields, use
  [Update a blog post](/api-reference/blogs/update-a-blog-post), which sends `PATCH`.
</Warning>

## Before you call

Register your store's credentials once when your app starts, as shown in
[Authentication](/authentication). Every SDK sample on these pages then gets its client in one line.
With cURL, send the access token in an `Authorization` header: `Authorization: Bearer $ACCESS_TOKEN`.

## Things to know

- **Wrap every request body in `blog`, comments included.** Send `{"blog": {...}}` to
  create, replace or update a blog post, and `{"blog": {"comment": {...}}}` to add a comment. A blog
  post write without the wrapper, or with an empty one, is rejected with `400` and the message
  `blog info missing`, and a field it does not recognise is rejected with `400` and the reason
  `unknown_field`. A comment that is not wrapped in both returns `404` with the message
  `comment is required`.
- **Deleting a blog post moves it to the trash, and no call on this API restores it or empties the trash.**
  The post leaves the listing and the count, and retrieving, replacing or updating it returns `404`.
  Its `title` stays taken: a create or replace with that title, in any letter case, is rejected with
  `400`, and the message says the title `is already used by a blog in the trash; restore or rename it`.
  Its comments stay readable and you can still approve them, but adding a comment to the post
  returns `404`.
- **In every comment response, the top-level `id` is the blog post's `id`, not the comment's.** One
  comment is returned as `{"id": <blog_id>, "comment": {...}}`, and the comment listing as
  `{"id": <blog_id>, "comments": [...]}`. Read the comment's own `id` inside `comment` and pass it
  as `blog_comment_id`. No call updates or deletes a comment.
- **A listing returns at most 20 blog posts per call, latest `date` first.** A larger `limit` is capped
  at `20`. To get more, send the next `page` or a higher `offset` while `pagination.has_next` is
  `true`. Only `limit`, `offset`, `page`, `sort`, `dir`, `ids`, `category`, `visibility`, `search`
  and `field_metadata` are accepted: any other parameter is rejected with `400`. To filter by several
  blog post `id` values, repeat `ids`, as in `ids=1201&ids=1202`: a comma list returns `500`.
- **After the listing rejects `limit=0`, a `sort` or a `dir`, your next request on the same client returns the same `400`.**
  It does so even when its own parameters are valid. The request after that runs normally, and so
  does every request on a new client: send the request that got the repeated `400` again.
- **A restricted blog post names its audience by each customer's `internal_id`.** Set `visibility` to
  `restricted` and `visible_to` to `selected`, and send `selected_customers` as
  `{"customers": [...], "groups": [...]}`, with each customer's `internal_id` from
  [List customers](/api-reference/customers/list-customers) and each customer group's `id`. A customer's `customer_id`
  there is dropped without an error, which leaves the audience empty. A post returns `selected_customers` as
  an object once it names anyone, and as `[]`, a list, while it names no one.
